# m-ex coverage for custom game modes

**Research date: 2026-09-27. Research only.** This is a source and documentation audit of the separate `melee/` `pc-port` checkout; no game was built or run for this note. It supersedes the **coverage count** in `docs/MEX_PORT_STATUS.md` §1 (the four-patch milestone), and the forward-looking SSS/ACE checklist in `_research/mex-stages.md` §11. Those files remain useful for their evidence and history. Here, **yes** means the core path is wired in current source, not full m-ex parity or a fresh runtime pass; **partial** means important data, call sites, or validation are missing; **no** means no m-ex-compatible path was found in the searched port source. Standalone PC features are identified separately.

## Sources and limits

- The **local m-ex checkout** is `_build/m-ex/`: its `README.md:1-17` lists fighters, items, stages, menus/scenes, effects/particles, sounds and music; `MexTK/include/mxdt.h:140-357` defines the `MexMetaData`, menu, music, stage, Kirby, fighter and scene tables; `asm/m-ex/` contains the actual injection families. This checkout is an ignored local reference, not vendored port code. `_research/mex-content-expansion.md` and `tools/mex_port/README.md` describe the 1,169-patch address inventory and the consult/reimplement attribution rule. No external feature list was needed.
- In the table, `mxdt.h` means `_build/m-ex/MexTK/include/mxdt.h`; bare game filenames such as `ground.c` mean `melee/src/melee/...`, and `gw_*.c` means `melee/pc/platform/...`. `MxDt.dat` is the content-table archive; `MxDb.dat` is a separate crash-symbol database, not a patch index (`tools/mex_port/README.md:46-61`).
- Port evidence is the current `melee/pc/platform/gw_mex*.c`, `gw_mods.[ch]`, `gw_mex_bridge.c`, and their `melee/src/melee/` call sites. `gw_mex_bridge.c:23003-23018` and `:27199-27215` map guest functions and static data to native addresses; `tools/mex_port/gen_bridge.py` generates it from the link map. A generated bridge is necessary but does not itself install every m-ex hook. `gw_mods.h:10-29,55-93` mounts mod packs and a single `MxDt.dat` per boot; it does not merge independent m-ex metadata tables.
- `_research/mex-stages.md`, `mex-css.md`, `mex-item-spawn.md`, `mex-sound-banks.md`, `mex-stock-icons.md`, `mex-dump-tools.md`, `mex-data-layer-design.md`, `mex-tier-c-*.md`, `mex-ppc-interpreter.md`, `mex-trophies-decision.md`, and `docs/HANDOFF.md` contain reverse engineering and earlier status. Several are **pre-implementation designs**: use the current source for current coverage. In particular, the older “Tier C cannot execute here” description is superseded by the PPC interpreter in `gw_mex_ftfunction_runtime.c:3363-3403`.
- The closest dated game-mode context is `_research/map-editing.md` (2026-09-27) and `_research/adventure-building-blocks.md` (2026-09-27). Both distinguish stage archive geometry/collision from Adventure `gm` progression and stage `gr` behavior. The proposed Lua platform/line/target additions in `map-editing.md:81` were **not in the main `melee/pc` source searched for this audit**; treat them as in-flight, not as a shipped interface. Tests cited below are existing source tests or historical run reports, not tests run for this note.

**Interpretation of “ported”:** The current port is substantially beyond the four patches counted at the top of `docs/MEX_PORT_STATUS.md`. Its later §6–8 already records more work, and many further modules have landed since. Conversely, an `MxDt` field, a broad `MELEE_MEX` flag list, or a passing structural test does not prove that a whole feature family behaves like m-ex in every game mode.

## Priority for a Subspace-inspired mode

Effort is for a **first useful slice** in this port: **S** = integration/content using existing interfaces, **M** = one reusable native subsystem, **L** = engine-wide or authoring-pipeline work. Art, writing and campaign-scale content are additional. Ranking combines leverage for large maps and encounter flow with what the m-ex port actually supplies.

| Rank | Partial/unported m-ex capability to finish or reuse | Leverage for GD's mode | Effort | Concrete first slice and dependency |
|---:|---|---|:---:|---|
| 1 | **Custom stage content pipeline and reliable stage slots** | A new map can be a named stage mod with its own `Gr*.dat`, collision, camera, file identity, SSS icon, audio and callbacks. This is the foundation for multiple rooms; the slot machinery is already present. | **M** for one authored room; **L** for a general large-map editor | Make one stage pack using an existing/new m-ex row, validate geometry versus `coll_data`, spawn/respawn points, moving-platform collision and current stage failures. A Lua platform/target overlay, once merged, can prototype pieces but cannot replace the archive's full visual/collision/camera contract (`_research/map-editing.md:85-125`). |
| 2 | **Custom item/enemy registration plus a spawn director** | Adventure enemies are item kinds. A reusable per-room enemy service gives real combat/traversal objectives and can reuse existing enemies before new assets. | **M** for an existing enemy; **L** for a freely authored roster and AI | On one authored room, register/preload one existing enemy, place deterministic spawns, and define defeat/despawn/cleanup. Then add a custom item or pickup through the partial `itFunction` path. `gd.items()` can inspect, not create, these objects (`_research/adventure-building-blocks.md:7-15,55-62`). |
| 3 | **Custom scene/mode graph and scene hooks** | Doors, checkpoints, boss encounters, cutscenes and return locations need a mode owner beyond a stage callback. m-ex scene tables offer a model, but their `MxDt.scene`/`ScFunction` path is unported. | **M** for explicit room transitions; **L** for seamless streaming or full m-ex scene compatibility | Extend the native LAB-style state-table precedent into a small room/encounter graph; use `gd.scene_launch` for prototype transitions and a versioned progress file. A bespoke native mode can be more direct than implementing every m-ex scene patch (`_research/adventure-building-blocks.md:31-39,47-55`). |
| 4 | **Mode menu and presentation hooks** | A selectable campaign entry, chapter/room picker, objective HUD and dialogue make the loop usable. `mexMenu` is absent, while `gd.kit` already covers drawing. | **S** for overlay/interstitial; **M** for a persistent native menu scene | Build a kit-driven selection/interstitial first, then add native menu registration only if the mode needs retail-style scene ownership and input/navigation across transitions (`docs/scripting.md:193-247`). |
| 5 | **Music and stage playlists** | Per-room music, boss cues and stage SFX add identity cheaply because the table/audio foundation is wired. | **S/M** | Put one BGM and one stage SSM entry in the mod's single `MxDt`, use the existing stage playlist for ambient selection, then add a mode cue/change API only when encounters require dynamic transitions (`ground.c:1998-2023`). |
| 6 | **Trophies/collection and custom fighter AI** | A persistent collectible gallery and new boss/minion behaviors matter later, but m-ex trophy save expansion and general AI authoring are large/unfinished. | **M** for a sidecar collection; **L** for native trophy parity/new enemy AI | Prototype collectible IDs in a versioned mode save with kit UI; use existing CPU fighters for a first boss. Defer 342-trophy gallery/save migration and new enemy behavior until the room loop works (`_research/mex-trophies-decision.md:23-53`). |

Custom stage **slots** therefore are not a zero-to-one port item now; the high-leverage gap is producing, mounting and validating large authored stages as repeatable mod content. A Lua-created platform/target is useful for iteration and for Target Test-style objectives, while a complete room still needs visuals, collision groups, camera bounds, authored points and deterministic encounter state.

## m-ex versus Geno/Lua: overlap and conflicts

| Area | Complement or conflict | Practical boundary for the mode |
|---|---|---|
| Content identity and loading | m-ex `MxDt.dat` assigns global fighter, item, stage and audio IDs; `gw_mods` overlays disc paths and permits **one** `MxDt.dat` per boot (`gw_mods.h:20-29`). Geno scripts and Lua mods load through their own manifests/files (`docs/scripting.md:61-99`). | A stage mod can carry Lua logic and m-ex-format assets, but two packs cannot each independently append `MxDt` rows without a metadata merge/registration service. Avoid assuming the file overlay composes global ID tables. |
| Fighter behavior | `ftFunction` guest PPC overrides engine callbacks; Geno adds native fighter states/articles, and Lua observes or makes narrow gameplay writes (`melee/docs/geno.md:1429,1879`; `docs/scripting.md:130-176,286-304`). | Define hook ownership per fighter. Both systems may want the same action, item or per-frame callback; replacing callbacks and clone-base fallbacks can silently suppress behavior (`gw_mex_ftfunction_runtime.c:3537-3549`). Geno is better for authored native fighter moves; m-ex is needed to run existing m-ex DAT fighters. |
| Stage geometry and targets | m-ex stage slots/`grFunction` load stage archives and code; the proposed Lua `gd.stage_add_platform`, `gd.stage_add_line`, `gd.spawn_target` would add runtime geometry/objectives if it lands. | Keep one collision truth and a deterministic load order. Runtime lines must agree with the archive's `coll_data` groups, moving JObjs, camera/blast bounds and rollback snapshots (`_research/map-editing.md:35-55,85-125`). These Lua calls were not found in current main source. |
| Enemies/items | m-ex `itFunction` supplies native-game item kinds and callbacks. Geno articles are fighter-owned projectiles; public Lua `gd.items()` is read-only for spawning (`_research/adventure-building-blocks.md:7-15,55-62`). | Use existing/item-system enemies plus a mode spawn service. Do not model hittable ground enemies as Geno articles without expanding their hurtbox, targeting and lifecycle rules. |
| Scenes/menus/HUD | m-ex has data-driven scene and menu tables, currently absent here. Lua has `on_scene`, `gd.scene_launch`, `gd.kit`; the LAB is a native mode precedent (`docs/scripting.md:130-144,193-247,293-304`; `melee/pc/geno/geno_lab_mode.c:158`). | Kit is fast for overlays and dialogue. A lasting campaign flow still needs native scene/mode ownership, transition state and save policy. `gd.scene_launch` is a transition command, not an m-ex `ScFunction` or full scene-table loader. |
| Determinism and online play | m-ex stage/fighter/item callbacks execute in game state; Lua hooks do **not** run on rollback resimulation, and Lua memory is not snapshotted (`docs/scripting.md:108-125`). | Keep encounter phase, enemy spawn state, moving platforms and pickups in deterministic/snapshotted native state if online co-op becomes a goal. Current netplay is scoped to a VS match (`_research/adventure-building-blocks.md:63-70`). |

## Ten-line summary

1. Local m-ex is `_build/m-ex`; its README and `MexTK/include/mxdt.h` define the comparison baseline.
2. The early four-patch status count is historical; current fighter, item, stage, audio and select code goes much further.
3. Fighter IDs, files, costumes and sound banks are wired, while arbitrary callback slots and some bridge calls remain limited.
4. Kirby hats and effects have data/call sites, with visual and capacity gaps.
5. Custom stage IDs, files, callbacks and SSS icons are wired, but some added stages have recorded failures.
6. m-ex supplies stage slots and runtime tables, not a large-map geometry, collision or encounter editor.
7. Custom item code works for proven articles such as Sonic's spring; a general enemy/pickup authoring API is absent.
8. Music/SSM/playlists are the cheapest m-ex content gain for a new room.
9. m-ex major/minor scene tables, `ScFunction`, `mexMenu`, full trophy expansion and general scene-exit hooks are unported.
10. Build a validated stage room, enemy spawning and explicit mode graph first; use Geno/Lua/kit where their narrower APIs fit.
