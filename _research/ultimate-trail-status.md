# Sora (`trail`) status-script findings

Research dated 2026-09-26. This note extends `_research/ultimate-sonic-blade-steering.md`; it supersedes that note only where a status branch is traced further below. Sources are `experiment/tooling/ultimate/workspace/extracted/prebuilt/nro/release/lua2cpp_trail.nro` in the read-only Ghidra project `${GW_GHIDRA_PROJECTS}/sora.gpr`, decompiled functions in `${GW_GHIDRA_PROJECTS}/sora_status/`, and `fighter/trail/param/vl.prc` decoded at `_build/tmp/sonic-steering-vl.xml` with ParamXML and `references/ParamLabels.csv`. Addresses are Ghidra virtual addresses. `confirmed` means an operation or value is present in these files; `inferred` means the gameplay interpretation or status-name mapping is not independently established. No external source or game run was used.

## 1. Counter rebound

| Finding | Evidence | Confidence |
|---|---|---|
| The Counter start status selects `special_lw_start` / `special_air_lw_start` (`0x10ef97f71f` / `0x146e22785f`) and installs a main callback. That callback toggles ShieldModule and ReflectorModule state from the `0xe618` and `0xe61c` work flags. | NRO `0x7100019d50`, `0x7100021240`; motion hashes verified with Hash40. | confirmed |
| The `game_speciallwstart` / `game_specialairlwstart` ACMD body turns `0xe61c` on at animation frame 8 and off at frame 26. The status callback uses this flag as part of the shield/reflector window. | ACMD dump files `${GW_GHIDRA_PROJECTS}/sora_acmd/game/0x5b268858f__0x13bc889263.c` and `...__0x16f7384849.c`, shared body `0x71000e5610` lines 12–104; status `0x7100021240` lines 88–164. | confirmed |
| The start callback checks work flag `0xe628`. If it is set, it calls `0x71000210a0`, which tests `StopModule::is_item`, `is_special_stop`, and `is_other`. After the remaining facing/`0xe62c`/`StopModule::is_hit` checks, the visible branch requests status ID from `const_value_table+0xe4ec` when `0xe630` is true, or `+0xe4f0` when false. The writer of `0xe628`, the meanings of `0xe630` and those two status IDs, and the full producer of the Counter collision event were not established in this pass. | NRO `0x7100021240` lines 164–281, helper `0x71000210a0`. | confirmed operations; meanings unresolved |
| A separate status entry switches motion to `special_lw_rebound` / `special_air_lw_rebound` (`0x129417320e` / `0x161969620f`) and shifts to main callback `0x7100020620`. That main callback requests `const_value_table+0xe4f0` when the rebound motion ends. This establishes the rebound state exists, but does **not** establish the incoming transition to it. | NRO `0x710001a370` lines 29–42 and 380–402; `0x7100020620` lines 20–42. | confirmed; trigger unresolved |
| The separate Counter attack entry selects `special_lw_attack` / `special_air_lw_attack` and, when a target object remains active, reads `rebound_distance_min/max` (0.9/4.3), scales them by 10, clamps absolute X separation, and interpolates a speed multiplier between front/back parameters. This attack setup does not prove what enters the rebound state. | NRO `0x710001e640` lines 50–64 and 208–384; `vl.prc` XML lines 999–1007. | confirmed arithmetic; relationship to rebound unresolved |
| `vl.prc` has `rebound_start_ground=25`, `rebound_frame_ground=1`, `rebound_start_air=30`, `rebound_frame_air=1`, `rebound_speed_y=0.02`, `rebound_speed_y_max=0.3`, `rebound_attack_start_frame=4`, `rebound_height=1.9`, and `rebound_approach=0.6`. The named start frames are parameter values, **not** independently verified transition frames. | `vl.prc` XML lines 985–1007. | confirmed values; timing unresolved |

**Answer:** the exact condition that selects the rebound status remains unresolved. The confirmed Counter-start branch above does not by itself prove that its `+0xe4f0` request enters rebound; rebound main also requests `+0xe4f0` at motion end. An implementation should therefore keep rebound as a separate state, use the parameter values only where their call sites are established, and leave the entry predicate explicit/replaceable.

## 2. Sonic Blade sampling, angle, and contact

| Finding | Evidence | Confidence |
|---|---|---|
| On a dash motion-end path, the status main samples **both** `ControlModule::get_stick_x` and `get_stick_y`, constructs a Vector2, and compares its length with `search_stick=0.25` before requesting the next status. This is a new sample for the next dash, not continuous steering during the current dash. The absolute animation frame of motion end was not proven. | NRO `0x710002bd30` lines 125–225; `vl.prc` XML line 652. | confirmed sample location; frame unresolved |
| A separate aim/effect helper reads both stick axes and computes an angle with `atan`; its use as the actual dash heading is inferred from its surrounding state path. Startup reads `search_frame=9` into work state, while `attack_turn_frame=4` is a parameter, but neither alone proves the exact stick-sampling frame. | NRO `0x7100027700` (also cited in steering note), `0x7100018d80`; `vl.prc` XML lines 651 and 659. | confirmed reads/values; timing inference unresolved |
| Dash initialization sets a directed velocity from cosine/sine of a selected angle. It applies `attack_up_speed_mul=0.85` when that angle is between `attack_up_angle_min=40` and `attack_up_angle_max=140` degrees. No status branch in this pass proves a 40-degree steering clamp or a turn-rate limit. | NRO `0x7100028750` lines 470–end; `vl.prc` XML lines 677–679; earlier steering note for arithmetic detail. | confirmed multiplier and range; clamp unresolved |
| During dash main, a nonzero ground touch flag enters logic that reads a touch normal and kinetic velocity, compares their angle with `attack_hit_ground_angle=65` or `attack_hit_down_angle=55`, and updates counters or changes status. There are separate status/situation branches for contact and landing. The touch-mask constants are imported through the value table, so this pass does not establish a unique wall-stop, wall-bounce, or landing transition for each surface. | NRO `0x710002bd30` lines 239–503; `vl.prc` XML lines 649–650. | confirmed operations; exact outcomes unresolved |
| The status checks for air-cliff transition and common ground/air transitions; the parameters include `attack_landing_frame=20` and `end_landing_fall_special_frame=20`. Which contact path uses each frame was not established. | NRO `0x710002bd30` lines 65–75 and 510–end; `vl.prc` XML lines 669 and 687. | confirmed calls/values; mapping unresolved |

**Answer:** the confirmed input sample is on the motion-end follow-up path. No exact fixed sample frame, steering clamp, or complete wall/landing outcome can be stated from the available trace. Do not equate the 40–140-degree speed range with an aim clamp.

## 3. Work flag at `const_value_table+0xe648`

| Finding | Evidence | Confidence |
|---|---|---|
| Dash initialization writes this flag with `WorkModule::set_flag`. The value is the conjunction of `0xe654` being true and `0xe660` being false. Immediately beforehand it copies another flag from `0xe650` to `0xe654`; then it clears `0xe65c` and `0xe650`. Thus the value is captured at **dash entry** from prior work flags. | NRO `0x7100028750` lines 95–162. | confirmed |
| The velocity helper reads `0xe648` and, when true, multiplies dash speed by unlabeled `vl.prc` parameter `0x1A41A10288=1.15`. The dash-2/3 game ACMD also reads the same flag to choose its attack branch at frame 3. | NRO `0x710002b2d0` lines 101–124; `${GW_GHIDRA_PROJECTS}/sora_acmd/game/` `game_specials2/3` bodies; `vl.prc` XML line 667. | confirmed |
| The NRO status pass found the copy/read of `0xe654` but did not identify its original setter, so calling it “previous dash connected” is plausible but unproved. `0xe660` is also read elsewhere in the side-special status path, but its exact semantic name was not established. | NRO `0x7100028750` lines 95–162; `0x710002bd30`; `0x7100018d80`. | inferred/unknown |

**Answer:** `0xe648` is set or cleared on entry to each dash from `0xe654 && !0xe660`; it is not set by the frame-3 attack script. Its input flags' producers and exact “hit connected” semantics remain unresolved. For an engine-neutral port, capture the prior dash's connected/target state before changing to the next dash, and do not read an action-local hit flag after that action reset.

## For the implementer

1. Model Counter start, attack, rebound, and end as distinct states. The observed guard runs shield/reflector logic during an ACMD-controlled flag window (frames 8–26), and its hit response is gated by work flags and stop state. Keep rebound entry as an explicit unresolved predicate; do not substitute the `rebound_start_*` parameter values for a proven trigger.
2. At Sonic Blade dash entry, copy the relevant prior-dash result before clearing the prior action's state. The NRO computes the dash enhancement flag as `previous_flag && !suppress_flag` from `0xe654`/`0xe660`; their source semantics are unresolved. Apply the 1.15 speed factor only when that copied flag is true.
3. Sample a two-axis stick vector at the follow-up transition; use magnitude threshold 0.25 for the observed branch. Set a directed velocity once per dash. Apply 0.85 speed for headings from 40 to 140 degrees. Do not add a 40-degree angle clamp or continuous in-dash steering without more evidence.
4. Keep wall/ground contact normal, velocity, and touch flags available to the dash state. The exact contact outcomes need a trace of imported touch-mask constants and status IDs before parity claims.
5. Keep Firaga/Blizzaga/Thundaga as three magic data cases and leave the cycle advancement event explicit. The NRO imports `change_magic`; the order and timing require the external implementation or a deeper call-site trace.
