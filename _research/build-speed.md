# Melee PC build speed: pipeline and opportunities

**Research snapshot: 2026-09-26.** This describes the scripts and local artifacts as inspected, without running clang, a build, or the game. It supersedes older timing claims in `docs/DEVLOG.md` (§5.3 says 989 TUs in ~30 seconds) for the current machine and 993-TU manifest; that older measurement used a different tree and workload. Times below are wall-clock estimates from log creation/end timestamps and object modification times, not instrumented stage timers. Concurrent lanes and machine load make them ranges, not guarantees.

## Stage map and current cost model

`build.sh` first compiles any explicit `--tu` or `--shim` arguments **serially**. Then it scans `_build/masstest/files.txt` and all game headers under `src`, `include`, `pc/geno`. A source newer than its object, a matching `<stem>_*.inc` newer than its object, or *the newest header anywhere in that tree* newer than its object makes the TU stale. The header search only considers headers newer than `files.txt`; it does not cover every compiler include root, notably `libs/dolphin` and generated `build/GALE01/include`, which is another reason to validate actual dependencies. CR is stripped from the manifest because a CRLF path silently skipped TUs in lanes. The 993-line loop invokes `echo | tr` for every object name and performs shell/stat work on Windows. Stale TUs go through `xargs -P 8` and `pipe_win.sh`: PPC-target clang (`-emit-llvm`, `-O2`, forced `math_ppc.h`) → `.bc` → `gwtool.exe` → x86 `.obj` plus `.imports`. Output `.obj.tmp` is **renamed** over `.obj` to avoid mutating hardlinked baseline objects.

The native shim scan takes the newest `pc/platform/*.h` and marks every older shim `.c`/`.cpp` object stale. It compiles those serially with i686 clang `-O2`; the three C++ shims use ImGui/Dawn includes and the dynamic MSVC CRT. It removes an old object before compiling, so a failed compile cannot leave a plausibly valid stale object. `slippi_build.sh` checks ENet headers/sources, conditionally compiles its eight C files, and writes `.slippi_link_objects.rsp` by filtering/augmenting the curated object list. The response files are inputs to the link; they are not a dependency graph and must not be replaced by a directory glob.

`gw_link` starts `build_melee_pc.bat` from `_build/ax86m` so the **83-library response file's relative paths** resolve, sets lane-local object response and outputs, and accepts only `MELEE_PC_LINK_OK`. The batch invokes MSVC `link` with `/INCREMENTAL:NO /OPT:REF /OPT:NOICF /BASE:0x10000000 /DYNAMICBASE:NO`, plus map and EXE output. `build.sh` then generates `gw_mex_bridge.c/.h` from this lane's map, symbols and splits, always compiles the bridge, links again, regenerates to test the fixpoint, possibly compiles/links a third time if it moved, and audits calling convention against the **final EXE**. There is no further regeneration check after that exceptional third link; a future optimization should make the loop explicitly converge or fail with a bounded retry count. The bridge has ~18,827 resolved function entries in the inspected logs. Both generated files are currently opened with `"w"` on *every* generator call, even if bytes are identical.

| Stage | (a) No-op request | (b) One game `.c` | (c) Widely included header | (d) New lane's first build |
|---|---:|---:|---:|---:|
| Game stale scan | ~90–115 s in recent quiet-ish beta runs; 6.7 min before first object in contended main full build | same scan | same scan | same scan; checkout/backdating overhead is separate |
| Game clang → gwtool | 0 | one TU, likely seconds, but no clean per-TU timer | current rule rebuilds up to **993**, observed ~9.2 min on main; other full-build totals 8.6–17.8 min | ideally 0 because `agent_new.sh` hardlinks baseline objects and backdates checkout; up to full rebuild if baseline/source/header state differs |
| Native shim + optional ENet | **48–50 shims every recent build**, ~30–35 s serially; ENet usually 0 | same | if a platform header also changes, same 48–50; otherwise still same due bridge header timestamps | usually same; missing/changed ENet objects add work |
| First MSVC link, bridge generation/compile, second link, final regenerate and ABI audit | ~8 s combined after last ordinary shim in beta example; individual substeps not timed | same, potentially changed bridge bytes | same, potentially changed bridge bytes | same |
| Total currently seen / expected | **~2–3 min** in common recent logs | **~2–3 min + one TU**, absent contention | **~9–18 min** when global header rule selects all TUs; highly load dependent | **~2–3 min after lane creation** if baseline aligns; **~9–18 min** if it does not |

The two counterintuitive parts are the long *no-work* shell scan and the repeated shim rebuild. On the latter, `gen_bridge.py` rewrites `gw_mex_bridge.h` during the previous build's final regeneration. Its mtime is newer than almost all shim objects. The next build's global platform-header rule therefore declares them stale, even though that generated header's content is unchanged. For example beta's header is stamped 18:55:42, after the ordinary shim objects at 18:55:02–34. `gw_mex_bridge.c` likewise gets a fresh timestamp and is compiled unconditionally. The 48–50 count is corroborated by dozens of consecutive beta logs, including builds with no stale game TUs. A one-file edit is therefore barely cheaper than a no-op build.

`agent_new.sh` hardlinks only baseline game and shim objects, copies required generated `.inc` files, backdates new checkout source timestamps by a minute before the oldest baseline object, and rewrites each response-file object path with quotes for the apostrophe/space checkout path. `lane_sync.sh` rebases, `touch`es changed `.c/.h/.inc` files so they cannot be missed by timestamp checks, and regenerates the lane response file in one `awk` pass. Backdating avoids a full false rebuild but can also hide **real content differences** from a baseline at another revision; any content-based cache must validate that case. It must preserve temp-write/rename for hardlinked objects and use the lane's own `symbols.txt`/`splits.txt`.

## Ranked changes: gain versus risk

1. **Stop timestamp churn in generated bridge files (high gain, low risk).** In `gen_bridge.py`, write `gw_mex_bridge.h` and `.c` to temporary files, compare bytes with existing files, and replace only on change. Have `build.sh` compile the bridge only when generated C or its true dependencies changed; after first link, compare regenerated content with the **bridge object known to be linked**, and skip bridge compile and second link only when unchanged. Retain the post-link fixpoint check and ABI audit; if content changes again, repeat generation/compile/link until stable with a bounded failure, closing the present third-link verification gap. This directly removes the observed ~30–35 s shim cascade and one link/bridge compile when stable. Verification: repeat a true no-op and a one-TU build, confirm `gw_mex_bridge.h` mtime stays fixed, 0 stale shims, and same generated bytes/map mapping; then force an address-changing object and confirm rebuild + final bridge fixpoint, entry count and 0 bad ABI prologues. Verify the changed log string exists in the final EXE, not a copied run EXE. The `--no-bridge` flag is not a substitute for this proof.
2. **Replace the 993-iteration shell stale scan with a batched dependency check (very high gain, medium risk).** A small Python driver can read `files.txt` once, stat paths in one process, and emit a NUL-safe stale list; first preserve the present conservative semantics, including CRLF, generated `.inc` and missing objects. Next capture each clang TU's actual dependencies (`-MMD/-MF` if it works with the PPC invocation) and native shim dependencies, including forced `math_ppc.h`, `build/GALE01/include`, Aurora, SDL, ImGui and Dawn generated headers. Use a hash of source and *transitive included bytes*, flags, clang/gwtool binaries and codegen configuration to decide whether an object is reusable. Keep timestamp fallback until dependency coverage is proven. This targets ~90–115 s of normal builds and prevents an unrelated header from rebuilding all 993; hashing **every header globally** without an include graph would preserve the over-rebuild. Verify a clean no-op, `touch` without content change, one source change, a narrow header, a widely included header, `*_*.inc`, generated includes, removed object, and a changed compiler/gwtool against the current conservative scanner. Include rebase/checkout tests: equal content must reuse safely, changed content must rebuild despite backdating.
3. **Make link conditional on changed inputs (high gain for no-op, medium risk).** Track hashes/identities of the exact lane-local object response contents and listed object bytes or validated object keys, 83-library response and referenced libraries, linker flags/tool version, map/EXE and bridge state. If all inputs and final artifacts are valid, a no-op should exit after the scan without either link. Keep `MELEE_PC_LINK_OK` for every actual link, and never use a failed link's old EXE. Verify by mutating one object, library, response-file line, link flag and bridge input separately; each must relink. A still-running EXE lock should still fail clearly whenever a link is needed. This is a further ~several seconds per no-op after items 1–2, plus avoids map parsing/audit when the final EXE is proven identical.
4. **Share content-addressed game TU results across lanes (high gain for first builds/rebases, medium-high risk).** Cache `.bc`, `.obj`, `.imports` by the full transitive input key, PPC clang flags/tool identity and gwtool identity. Populate lane outputs by hardlink/copy only after the cache entry is complete; always replace lane entries atomically. Never compile directly into a shared hardlinked inode. A fresh lane with a different checkout timestamp but identical content could then hit ~993 cache entries; changed inputs would compile exactly the affected set. Validate cache hits by comparing object/import hashes and final link/bridge results with a clean build of the same revision. The current hardlink seed already makes an identical *baseline* first build cheap; the cache is valuable chiefly after branches diverge or a header timestamp causes a false full rebuild.
5. **Tune parallel compilation after the scan is fixed (medium gain, low-medium risk).** Game TUs use fixed `xargs -P 8` on a host exposing 20 logical processors. Benchmark 4/8/12 (and perhaps 16 only if RAM and commit headroom allow) with stage timers and other lanes idle. Limit total concurrent jobs across lanes, and parallelize independent native shim compiles with unique temporary outputs and fail-fast result collection. The ~30–35 s serial shim span is the immediate target. Do not assume per-core scaling: Windows process startup, storage, memory/commit pressure and concurrent games may dominate. Verify equivalent `.obj` hashes where deterministic, identical bridge entry count and ABI audit, and no shared-inode mutation or missed compiler failure.
6. **Try a faster linker in an isolated comparison (possible medium gain, high risk).** MSVC `/INCREMENTAL` might save a link but may conflict with `/OPT:REF`, map layout and the required `/OPT:NOICF`; it can also make addresses shift differently between passes. A pinned-base `lld-link` experiment is another option. Benchmark first/second link separately with the same 1,037-object/83-library response files and compare EXE behavior, map symbols including statics, section/base layout, native-data ranges, bridge fixpoint and crash-map resolution. Do not accept a smaller map or a green boot as proof. Reducing objects or combining TUs is lower priority: 993 game objects total only ~10 MB here, and unity builds may change symbol names/static ownership that `splits.txt` uses.
7. **Use a PCH only if the remaining C++ shim time warrants it (small gain, medium risk).** `gw_console.cpp`, `gw_overlay.cpp`, and `gw_fx_render.cpp` reach ImGui/Dawn headers; `gw_overlay.cpp` took several seconds in the beta span. A PCH must be keyed by C++17 versus C++20 mode, `/MD` equivalent, target, macros, include paths and generated Dawn headers. Measure each shim first; after item 1 a normal build should compile none of them, so a PCH mainly helps real C++ header or source edits. Verify cold and warm object/link equivalence and invalidation on a Dawn/ImGui header change.
8. **Profile the separate Ultimate installer cold path (large absolute gain, separate scope, medium risk).** The reported cold conversion is ~16 min for ~70 clips (~14 s/clip of wall time, *not* necessarily CPU time). `ports/ir/tools/install_ultimate.py` already uses a content-keyed per-clip pickle cache and `ProcessPoolExecutor`, defaulting to at most 4 workers; it halves workers after memory/paging failure. The per-worker conversion decodes a clip, optionally bakes helper joints, fits figatree curves and checks world poses at integer and half frames, potentially retrying the fit up to seven times. Instrument per-clip decode/bake/fit/check/cache hit and peak commit; profile the slowest clips and repeated `check()`/SciPy work before changing algorithms. Then test bounded worker counts with enough memory, cache reuse for script-only reinstall, and more selective conversion of requested clips. Verify resulting animation bytes/clip count, per-joint world-error bounds including half frames, root-motion variants, and in-game playback before treating a faster conversion as equivalent. This does **not** shorten `build.sh` itself.

## Five-line summary

Current quiet builds often spend ~2–3 minutes even with no stale game TUs.
The biggest observed no-op costs are ~90–115 seconds of shell scanning and ~30–35 seconds of repeated shim compilation.
The shim cascade comes from unconditional rewrites of generated `gw_mex_bridge.h`; write only on content change first.
Full 993-TU builds took roughly 9–18 minutes in recent logs, with fixed `-P 8` and large load variance.
Preserve atomic lane objects, exact response files, and the final bridge/map/ABI proof while optimizing.
