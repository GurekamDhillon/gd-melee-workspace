## What the owner wants
"I still want maze style generation. Hand built levels are important as well." Mazes are generated by stitching hand-built
chunks. Design sources: `docs/PLAN-ENVOY-EDITOR-MISSIONS-2026-10-03.md` section 4a,
`docs/superpowers/specs/2026-10-03-mission-folders-and-large-levels-design.md`,
`_research/large-levels-and-maze-stitching-2026-10-03.md` (the toy maze that already ran: chunk format, 120x100 chunks,
streaming cost, limits), `docs/superpowers/specs/2026-10-03-supertime-envoy-design.md` section 8 (runs use mazes).
Facts measured in the game today: walls stop fighters from outside; floors are pass-through from below unless a piece is
marked `gd_solid`; a doorway has no collision (walk through along X); Ganondorf is 17.97 tall and 11.1 wide; a full hop
reaches about 29 units, a double jump about 52; chunk streaming keeps the 3x3 neighbourhood; each chunk has its own spawn;
camera modes exist per chunk (`camera = {mode="chunk", ...}`).

## Build
1. **Chunk contract** (document it; extend the exporter validation only if needed): a chunk is a mission chunk folder with a
   declared size (default 120x100) and `exits`: for each side (left, right, up, down) zero or more door slots at fixed,
   standard positions (so any two chunks with matching slots join), each tagged with how it is traversed (walk, drop, climb:
   needs platforms within jump reach in the lower chunk) and optional tags (`start`, `goal`, `boss`, `shop`, `secret`,
   difficulty, theme, enemy budget, which enemy kinds may spawn where). Author side: markers in Blender
   (`gd_exit=left|right|up|down` with a slot index) exported into the chunk level file.
2. **The generator** (pure, deterministic from a seed, with an injected random source; no engine calls; usable from Lua at
   run time and from Python for offline batch checks: one implementation, the other a thin port or a call-through, say
   which): lays chunks on a grid to build a maze with a guaranteed solvable main path from `start` to `goal`, optional
   branches, loops and dead ends with rewards, a target length/size and difficulty curve, vertical sections (climb up via
   platforms, drop down), and constraints: every exit slot either joins a matching slot or is sealed (the generator picks a
   sealed variant or adds a wall piece: decide and document), no unreachable chunk, traversal respects the measured jump
   reach (a climb exit is only used when the chunk below provides the platforms), enemy budget per chunk scaled by distance
   from start. Output: a mission folder (level + mission files referencing chunk folders at grid offsets) that the missions
   mod loads as-is.
3. **Solvability checker**, separate from the generator: given the output, proves start to goal reachability over the exit
   graph using the traversal tags, and reports unreachable chunks, unsealed exits and overlaps. Run it over 1,000 seeds in the
   tests.
4. **A starter chunk set as data only** (no art, no models: built from the existing kit part names so the exporter and kit
   can fill them): corridor, corner up/down, T-junction, room with platforms, shaft segment, drop, dead end with reward,
   start, goal, boss room. Enough for varied mazes of 8-20 chunks. State each chunk's exits in a table.
5. Missions-mod console commands: `mission maze <seed> [size]`, `mission maze reroll`, and a text map dump of the generated
   maze (ASCII grid with exits) to the log for debugging; the debug fly commands must work across it (`mission tour`).
6. Tests (written first): determinism per seed, solvability over 1,000 seeds, every constraint above, exit sealing, size and
   difficulty targets, the ASCII dump, and that output validates under the missions mod's validator.

Report `_build/tmp/codex-maze-generator-report.md`: the chunk contract, the algorithm in a page, the starter set table,
tests, what could not be verified without the game (traversal feel, jump reach assumptions per character), and a native test
plan (seeds to try, what to look for, using `mission tour` and `gd.wait_until`).
