# Lane packet: Envoy co-op, offline and synthetic (2026-10-05)

Lua and Python only, in the Envoy mod (`melee/pc/scripts/examples/envoy/`, its tests, `tools/port/envoy_bundle.py`). No
engine edits, no build. Start only when no other lane is editing the Envoy mod. Read `CLAUDE.md`, `docs/scripting.md`,
the mod's `MENUS.md` and `PLAYTEST.md`, `_research/envoy-netplay-scoping-2026-10-05.md` (the online plan this prepares
for: read all of it, especially "the mode itself online" and "what to stop doing now"), `docs/HANDOFF-2026-10-05.md`,
and how earlier lanes drove runs without a human (`_build/audit-20261003/adventure/`, `envoy-join/`, `verify-runs/`:
the debug fly cursor `gd.fly_target` / `gd.fly_attack`, `uxdump`, `uxpress`).

## The owner (verbatim)
"I actually also envisioned envoy supporting our custom online netplay. two player, cooperative or adversarial envoy."
Then: "can you debug fly two coop clients together to test coop "synthetically" through a few new games?" Two networked
clients cannot run Envoy yet (netplay is one-on-one human Versus; script gameplay writes and the fly cursor are refused
online). Agreed instead: co-op in ONE game instance, two player slots each with a build, both driven by the fly cursor
through a run and a few New Game+ loops, to settle the DESIGN before any netcode. He approved the Versus-style shape.

## Build
1. **A co-op run as a sequence of Versus-style team stages**, not retail Classic (this is the shape the port's netplay
   could later run): two player slots on one team against opponents generated by the run (count, fighters, builds from
   the real roller), stage by stage, with the run's own between-stage flow (results, reward screens, next stage) and
   New Game+ looping. Decide how stages are sequenced and ended using what the engine offers offline today (scene
   launch tokens for a Versus team match, `gd.match_end_hold`, the stage-clear flow the mod already drives): report
   what was missing. Reuse the run host, economy, merge, keystone and progression modules: a co-op run must not fork
   them; where they assume one player, generalise to N players (N = 1 stays byte-for-byte the current behaviour: prove
   it with the existing tests).
2. **Take the simplest sensible rule for each open design question, behind a named tuning value, and list them for the
   owner to overrule**: each player has their own build, bag and keystones (shared nothing by default); each player
   gets their own offers at a reward screen (how two players use one screen on one machine: side by side, or in turn;
   online each would see their own); floor drops belong to whoever touches them first, with a switch for "owned by the
   player who caused them" and one for "duplicated for both"; opponents scale to the TEAM (propose the formula: for
   example the stronger build plus a share of the other, or the sum with diminishing returns: measure both); opponent
   count and stocks per stage; what happens when one player loses all stocks (spectates until the stage ends and
   returns next stage: default; or the run ends); starting keystones (one each, different); synergies ACROSS players
   (a status one player applies that the other's drive reads: on by default? it is the most interesting co-op idea:
   make it work and say what it does to balance); friendly fire off.
3. **Two build strips and readable ownership**: each player's strip, pickups and announcements are unmistakably theirs
   (port colour); the inventory grid opens per player.
4. **Keep it netplay-ready**: every decision a pure function of (run seed, stage, loop, player index) and game state;
   no wall clock, no per-peer input in rules; each player's choice an explicit recorded event (so that online it
   becomes a message to the other peer); a compact run record for both players with a digest. Note every place where
   one machine lets you cheat on that (both players' choices available at once) and how online would differ.
5. **Drive it synthetically**: both players flown by the debug cursor (and, as a second policy, as CPUs with
   `gd.cpu_assist`), reward choices made by seeded policies, through a full run and at least three New Game+ loops,
   several seeds, with the fast virtual clock where the host tolerates it. Record per stage: both builds' strength,
   opponents' strength, who dealt and took what, drops and who got them, time to clear, any softlock, script error or
   stuck screen (exact log lines), script cost with two builds and many opponents (target: under about 1 ms a frame).
6. Lua tests for the N-player generalisation and each rule; bundle regenerated and checked; docs; an owner launch
   script for two local controllers.
Report: the mode as built, the rule table (default, alternatives, what the synthetic runs showed for each), balance
findings for a team, everything that broke, the list of engine capabilities online co-op would need beyond the scoping
study's, and what could not be tested on one machine.
